# i18n — som-blocks

- Languages v1: `es` (default and source language, Chilean Spanish, tú form) and `en`. Planned: pt, zh-Hans, ja, fr, it, de.
- One list drives everything: `SUPPORTED_LANGS` in `src/i18n/messages.ts`. `Lang` is derived from it, and every per-language map is typed `Record<Lang, …>`, so a new entry does not compile until each map has it.
- Three message layers, all flat keys:
  1. **Blockly core** (context menus, trashcan, core block labels): ship with Blockly as `blockly/msg/<lang>`, imported in `BLOCKLY_CORE_MESSAGES` (`src/blocks/registry.ts`). Blockly's files are complete (its build fills gaps with English).
  2. **Block families**: each family module carries its own `messages: { es: {…}, en: {…} }`, keys namespaced by family (`SOM_SERIAL_PRINT`, `SOM_IO_CATEGORY`), referenced from block JSON and toolbox as `%{BKY_KEY}`. A family may also override a Blockly core key.
  3. **UI**: `src/i18n/messages.ts`, `UI_*` keys, read with `t(key, lang)`; `format()` fills `{name}` placeholders.
- Rules: one key per literal even if the text repeats; every language is edited in the same PR; no user-visible literal in components or block definitions.
- Fallback: a key missing in a language shows the `es` text (`t()` for UI, `applyLocale()` for families). Dev builds log one console warning per missing key; production stays quiet. The CI check below is what stops it from merging.
- Locale at startup: URL `?lang=` > saved preference (`localStorage` `som-blocks.lang`) > browser language > `es`. The header switch (language names in their own language, never flags) changes everything live, saves the choice and drops `?lang=` from the address, so a reload keeps it. A `?lang=` link still wins for the load it opens.
- Changing language relabels the Blockly workspace in place: new messages, rebuilt toolbox, and the blocks re-created from their own state (labels are fixed when a block is created). It is the same workspace, so blocks, undo history, zoom and scroll survive. New projects get the new language's default name.
- Audience 10–14: short imperative labels, no jargon on the starter toolbox; technical terms allowed in the full toolbox and code view.

## CI check

`pnpm i18n:check` (`scripts/check-i18n.ts`, core rules in `src/i18n/check.ts`) runs in the CI editor job and fails, with a list, when:
- a UI dictionary or a family's messages have different key sets in `es` and another language (missing or extra keys);
- a key is unused: no string literal `'KEY'` and no `%{BKY_KEY}` anywhere in `src/` or `e2e/` (tests count; a family key that overrides a Blockly core key counts as used). Build keys as whole literals (a lookup table of `MessageKey`s), never by concatenation, or the check cannot see them;
- a `%{BKY_…}` reference in a family's blocks or toolbox has no message in that family or in Blockly core.

## Adding a language (e.g. `pt`)

1. Add it to `SUPPORTED_LANGS` and its own name to `LANG_NAMES` (`src/i18n/lang.ts`).
2. Add the Blockly core import (`blockly/msg/pt`) to `BLOCKLY_CORE_MESSAGES`.
3. Add a `pt` dictionary in `src/i18n/messages.ts` and a `pt` block in every family's `messages` (`pnpm typecheck` lists the families).
4. Run `pnpm i18n:check` until it passes, then have a native speaker review student-facing copy for ages 10–14.
